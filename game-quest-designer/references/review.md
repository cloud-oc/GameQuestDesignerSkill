# 任务评审与验证

根据本次范围选择检查维度，不把通用偏好作为项目硬标准。

| 维度 | 核心问题 |
|---|---|
| 叙事 | 动机、信息揭示和转折是否有因果？玩家会不会依赖尚未获得的信息？ |
| 体验 | 当前目标是否可理解？玩家行动是否有反馈？重复与移动是否有目的？选择后果是否可感知？ |
| 逻辑 | 前置和结束是否完整？分支能否到达合法终态？提前完成、重入、重复事件是否留下错误状态？ |
| 系统 | 关键行为是否有项目能力依据？未知能力是否被冒充为支持？是否遵循真实 schema？ |
| 制作 | 资源与演出是否支持所述行为？隐含需求、共享依赖和变更影响是否遗漏？ |

每条问题给出定位（任务/节拍/节点）、依据、触发场景、影响、建议修订及验证方式。区分阻塞、主要体验问题与可选优化；没有足够证据时提问或标风险，不报确定缺陷。

修订优先保持原叙事意图和现有能力，说明必要取舍。更新相关流程和需求，检查修订是否产生新的矛盾。用户只要求评审时交付建议；明确要求修改时落实改稿。

## 以场景走查

为关键分支及相关异常记录：初始状态 → 玩家操作或系统事件 → 预期结果 → 依据/未知项。至少覆盖本次设计中的正常路径和最可能导致阻塞的路径；不要套用与任务无关的测试清单。

例如：玩家接取前已持有道具 → 接取任务 → 若系统支持追认则目标完成，否则设计应说明补救；事件到达两次 → 奖励不可重复发放，但需确认项目实现机制。

区分验证层级：

- 文档走查：检查设计中声明的逻辑是否自洽。
- 配置验证：运行真实 schema 或项目校验工具，记录输入与结果。
- 引擎/游戏验证：实际执行场景，记录环境与观察结果。

只能报告已完成的层级。没有引擎不能声称任务可运行；没有实测不能把目标时长当体验结果。
