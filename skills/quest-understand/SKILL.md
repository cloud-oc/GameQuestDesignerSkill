# 任务系统理解

## 开始之前
先看用户提供的项目资料和模板，只做这次需要的内容。资料不全时，可以先写草案，把假设和待确认的问题说清楚。沿用已有编号，注明关键规则的来源；其他项目的做法只能作为建议。
涉及引擎配置时，以真实格式和项目能力为准。交付时说清检查过什么：文档走查、配置校验和引擎运行是不同的验证，不能互相替代。

## 怎么把设计说清楚
像向一起做任务的策划说明方案：先讲玩家遇到什么、要做什么、会发生什么，再补规则和制作细节。每段围绕一个问题，优先用完整短句；只有需要对照条件或分支时才用表格。
首次出现“节拍”“状态”等术语时，用当前任务解释。例如“询问船工后，玩家得知货物被运往旧仓库”，比“完成信息反馈与状态流转”更清楚。沿用项目已有术语，但不要堆叠抽象名词。
创意草案先让人读懂故事和玩法；交接规格再补编号、条件和字段。把事实、建议与待确认事项分开说明即可，不必给每句话贴标签。

## 分析方法
从用户提供的系统说明、schema、编辑器资料和完成案例交叉提取规则。案例证明该用法存在，不代表相似用法均受支持。
首次建立项目画像、项目规则分散或用户希望形成可复用约定时，读取并按需复制 [项目规则摘要模板](assets/quest-project-contract-template.md)。用它整理会影响这次设计的规则即可，不必逐项填写。想看项目规则怎样影响任务设计时，读取 [虚构项目契约示例](references/project-contract-example.md)。
逐项识别：真实任务层级；接取/推进/失败/重试/结束生命周期；条件组合；计数范围；事件执行方；状态持久化；奖励结算；场景与多人归属。仅研究项目涉及的部分。
把玩家可见状态与内部状态分开，说明状态归谁维护、由谁推进、在哪保存。条件、瞬时事件与持久结果不得混为一谈。
同一字段在多份材料中冲突时，保留双方来源与影响，依据用户指定权威或实际 schema 解决；日期新不自动代表有效。
## 交付
读取代码或配置资料时，沿一个实际推进过程定位：配置装载 → 条件计算/事件监听 → 状态写入 → 表现刷新 → 奖励结算 → 存档恢复。为环节记录真实文件、符号或配置行；找不到的环节保留未知，不编造标准引擎架构。
额外检查世界事实与任务局部变量是否混用、事件是否携带实例标识、配置 ID 是否跨版本稳定。项目画像应让设计师知道哪些状态可可靠依赖，开发者知道哪些映射需要核验。
按需给出结构图、状态转换表、能力表（已支持/不支持/未知、约束、依据）及本项目工作流。
每个关键未知项说明它阻塞哪项设计决定。输出足够供后续设计复用的结论，不复制整份资料。
## 交付前检查
任取一个已有任务，沿入口、条件、动作和终态解释一次；解释不了的环节标成缺口。项目切换后不继承上一项目的节点、资产或组织规则。
