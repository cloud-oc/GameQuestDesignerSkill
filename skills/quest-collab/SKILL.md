# 任务跨团队交付

## 开始之前
先看用户提供的项目资料和模板，只做这次需要的内容。资料不全时，可以先写草案，把假设和待确认的问题说清楚。沿用已有编号，注明关键规则的来源；其他项目的做法只能作为建议。
涉及引擎配置时，以真实格式和项目能力为准。交付时说清检查过什么：文档走查、配置校验和引擎运行是不同的验证，不能互相替代。

## 怎么把设计说清楚
像向一起做任务的策划说明方案：先讲玩家遇到什么、要做什么、会发生什么，再补规则和制作细节。每段围绕一个问题，优先用完整短句；只有需要对照条件或分支时才用表格。
首次出现“节拍”“状态”等术语时，用当前任务解释。例如“询问船工后，玩家得知货物被运往旧仓库”，比“完成信息反馈与状态流转”更清楚。沿用项目已有术语，但不要堆叠抽象名词。
创意草案先让人读懂故事和玩法；交接规格再补编号、条件和字段。把事实、建议与待确认事项分开说明即可，不必给每句话贴标签。

## 协作方法
先明确接收方和本次决策：实现功能、确认资源、评审方案或处理变更。以其需要的业务信息组织材料，不堆叠所有设计文档。
写明变更原因、改前与改后、玩家在不同状态看到什么/知道什么/做什么，以及受影响的任务、地图、追踪、手册和线索。
向程序交接条件、状态归属、异常和数据接口；向关卡交接点位、可达性、角色占用与表现阶段；向演出交接叙事目的、控制权与恢复；向界面团队交接信息优先级、状态规则与反馈。
## 依赖与验收
向开发和测试交接时，对齐同一组任务、规则、资源和测试 ID。标出已确定的体验要求、待选实现方案与当前阻塞，避免把实现建议当成唯一验收方式。
改动涉及旧存档、共享角色或奖励时，附受影响阶段与回归范围；涉及对白和演出时，附文本版本及需要重新制作的内容。
交付标准按实际证据说明：设计评审已完成、配置校验已完成、指定构建运行已完成、试玩问题待复核。没有记录就不把阶段标为完成。
每项依赖写输入、期望输出、前置条件、来源 ID 与可观察验收。用具体玩家场景定义完成标准。
范围分为交付必需与可后置，依据设计目标说明取舍；没有团队信息时负责人待分配，不虚构确认或排期。
## 交付
给出交接简报、变更影响表、决策待办。未决问题说明选项与影响，避免“请相关方确认”式空泛表述。
文案和材料生成不等于已发送、已评审或已批准。仅在用户明确要求发送时使用相应工具，并核对目标。
