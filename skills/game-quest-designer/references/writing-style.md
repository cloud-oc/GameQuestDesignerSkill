# 把任务设计写给人看

读者通常是一起做任务的策划、程序、美术或测试。让他们先看懂发生了什么，再找到自己要做的事。术语和编号用来帮助定位，不能代替解释。

## 先写一段能想象的任务

> 港口的记账员失踪了。玩家找到一张被改过的货单，向船工打听当晚的装船情况，再决定把账本交给卫队，还是替记账员隐瞒行踪。选择会改变船长之后是否愿意提供帮助。

这段已经说明人物、线索、玩家行动和后果。接下来再按需要展开条件和分支。用户只要创意时，不必附完整编号表。

## 抽象表达怎么改

| 原写法 | 更清楚的写法 |
|---|---|
| 通过信息增量兑现玩家承诺 | 玩家对比货单和船工的说法，发现船长隐瞒了目的地。 |
| 维护状态闭环与异常恢复 | 玩家交出账本后记录这一结果；读档时从质问船长继续，不再要求找账本。 |
| 保持全链路追溯 | 在仓库场景需求旁注明对应任务和检查方法，方便关卡与测试找到它。 |
| 降低分支组合爆炸风险 | 两条调查路线在仓库汇合；只保留“是否答应保护船工”这一差异。 |
| 增强角色塑造与沉浸感 | 船工先否认见过记账员；看到求救信后，他压低声音，告诉玩家后门的位置。 |

这些是虚构示例，不是本项目已支持的功能。

## 术语要落到当前任务

- **项目契约**：项目规则摘要，说明哪些玩法和资源可用、哪些还不确定。保留真实文件名。
- **玩家承诺**：这个任务让玩家期待的体验，例如“靠自己找出谁在撒谎”。
- **玩家动词**：玩家实际能做的操作，例如观察、询问、交换和潜行。
- **节拍**：一小段有明确变化的流程，例如从“寻找证人”转到“查证证词”。
- **完成条件**：系统凭什么认定这一步结束。不要只用“调查结束”解释“调查结束”。

技术规格中的字段名、枚举、API 和 ID 保持原样。在旁边补解释，不改成不准确的口语。项目已有定义时以项目为准。

## 按读者需要展开

概念稿可以用“任务概况 → 玩家怎么参与 → 选择与结尾 → 制作难点”。逻辑稿可以用“触发条件 → 玩家操作 → 系统结果 → 中断后怎么办”。这是可选组织方式，不是每次必须填完的模板。

段落说明因果，列表列步骤，表格比较分支。不要让一句话承载一整套流程，也不要把所有短句都拆成项目符号。交付前读一遍：读者能否复述玩家要做什么，以及团队还需要确认什么？
