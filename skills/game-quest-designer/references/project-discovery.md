# 项目探索与工作流适配

目标是生成这个项目能实际使用的工作约定，不是填写一张通用问卷。

## 建立依据

先盘点用户提供的任务系统文档、编辑器说明、配置 schema、已完成案例、剧本、世界观、资产目录和制作规范。按当前交付选择阅读范围。案例能证明一种用法存在，不能证明所有类似用法都支持。

为影响设计的结论保留：结论、状态（明确陈述／推导／建议／待确认）、来源及位置、适用版本。资料缺页、无法访问或互相冲突时记录缺口和影响。用户明确指定权威资料时遵循其优先级。

## 形成项目画像

根据资料提取相关维度，不要求每项都有答案：

- RPG 类型、核心玩家行为、叙事语气、任务在游戏中的作用。
- 项目真实层级与术语：任务、阶段、目标、事件等之间的关系；没有依据时不假定存在这些层级。
- 接取、激活、推进、结束、失败、放弃、重置和重复的生命周期。
- 条件、事件、计数、变量、分支、并行、演出、NPC 控制等能力及限制。
- 世界状态、场景切换、存读档、NPC 生命周期；多人或联机只在项目适用时研究。
- 编辑器或配置输入格式、必填字段、标识规范、关联方式及可用验证工具。
- 现有资产和可复用玩法，以及实际说明的团队职责、评审和交接方式。

能力记录可采用：`能力 | 已支持/不支持/未知 | 约束 | 依据 | 设计影响`。将“明确不支持”和“文档没写”严格分开。

## 从画像导出项目工作流

用项目的真实术语说明：输入资料 → 设计步骤 → 每步输出 → 检查方式 → 下游交接。只有资料确认时才指定团队或岗位负责人，否则标为待分配。不要自动要求跨团队签字。

例如，资料若说明任务通过事件表推进，就围绕事件与条件建立逻辑流；若使用节点图，就采用其已知节点类型。既没有 schema 也没有节点说明时，先交付中立行为与状态描述，把映射列留待验证。

适配至少应体现在术语、能力边界、输出字段和验证方式中；不能只替换项目名称。优先沿用用户模板，删去不相关的通用字段。

无资料时，输出简短的临时工作约定和当前未知项即可。允许先创作，不把临时建议当成项目规范。对阻塞问题说明“缺少什么、会影响哪项决定”，方便用户补充。

## 复用与更新

可将画像与工作流分别保存为 `project-profile.md`、`workflow.md`，或并入用户已有资料。注明项目和所依据的版本。新资料到来时更新变化的结论，并列出受影响的任务、系统映射和需求；保持其他项目隔离。不要因每轮请求重建同一套材料。
