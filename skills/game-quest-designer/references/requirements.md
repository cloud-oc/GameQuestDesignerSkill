# 隐含制作需求提取

沿任务流程逐步检查“这一体验必须由什么支撑”，不能只搜索剧本里的名词。例如“NPC 递信”除角色与信件，还可能需要递接动作、手持位置、道具可见性和交互时序；这些实现方式先作为候选，已有通用交互也可能满足需求。

按相关性扫描：角色模型与外观、动作与表情、道具与图标、特效、对白与配音、音乐和音效、镜头与演出、关卡点位与通行条件、交互物、UI 提示、玩法和系统扩展。按资料明确的职责归属分组；未知负责人标为待分配。

## 将两个状态维度分开

- **需求依据**：明确（资料直接要求）、推导（实现某节拍可能需要，说明原因）、待确认（意图或规格不清）。
- **资源供给**：已存在且适配已确认、复用候选且适配待核对、需新增且依据明确、未知。没看到资产目录不能直接判为需新增；项目有同名模型也不代表绑定、外观和演出适配都已确认。

建议最小记录：`需求 ID | 类别与描述 | 来源任务/节拍 | 需求依据 | 资源供给 | 规格/验收点 | 依赖与待确认项`。依照用户表格增删字段。

把数量、版本、形态和使用条件写到足够核对的程度；没有依据就保留未知。区分“需要能表现递信”与“必须新做一套递信动画”。不凭空承诺工期、预算或人员安排。

## 跨任务汇总与变更

同一模型可以跨任务复用，但服装、动作适配、角色身份和状态差异可能是独立需求。用规范化名称加关键规格寻找重复项，合并时保留所有来源与使用条件；有冲突的规格单独列出，不能仅按名称合并。

修改任务后把需求标为新增、变更、沿用或不再需要，并保留受影响来源。移除某一节拍后，只在没有其他任务引用时才建议撤销共享需求。

交付应让制作方能回答：为何需要、用于哪里、已有资源能否满足、还缺什么。资源提取不是对实际资产库的验证；未查询资产库就明确说明供给状态未核实。
