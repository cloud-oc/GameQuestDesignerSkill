# 任务系统与制作管线

仅在项目资料确认采用此模型时使用。以下是开发文档给出的公司管线基线；若当前项目资料不同，以当前项目为准并记录差异。

## 系统职责

任务系统负责展示当前目标、记录目标完成、更新下一目标，并通过监听游戏逻辑事件驱动持久状态流转。它不是默认的演出调度器。

层级模型：

```text
章节 Chapter
└─ 幕 Act ↔ 任务组 Quest Group / 父任务
   └─ 任务 Quest
      └─ 目标 Target
```

- 幕是叙事切片，与开发层任务组映射；从“开启父任务”开始，以“父任务成功”结束。
- Quest 记录和流转持久状态，在关键节点注册条件或动作。
- Target 检查状态或行为，完成后推动所属 Quest。
- 玩家可见层级与开发层级可能不同，不能把内部子任务标题默认当成玩家文案。

## 生命周期

基线状态为：`未激活 → 不可领取 → 可领取 → 进行中 → 可交付 → 已交付`，并可能进入 `已失败`。其中可领取、进行中、可交付通常对玩家可见。

领取和提交模式可能为 `Null / Auto / Npc / Other`：

- `Auto`：条件满足后自动领取或提交，是常规任务表达候选。
- `Other`：任务本身不控制流转，由外部事件接取或结束；必须说明状态所有权与恢复方式。
- `Null`、`Npc` 的确切语义以项目配置说明为准，不凭名称补全行为。

## 触发器、事件与表现层

- 触发器表示条件或监听，常见参数包括统计类型、输入参数、运算符和目标值。
- 事件执行外部逻辑。事件能否恢复、能否重复、由客户端还是服务端确认会直接影响任务安全性。
- 开发文档将对话/引导类事件列为当前风险用法，因为断线重连可能丢失。检查时要依据当前事件库和恢复机制，不能永久认定所有同类事件非法。
- 若项目采用 CBT3 声明式方向，任务层声明关键目标和可靠服务端条件；NPC 调度、对话、镜头和演出由 Sandbox 等可重入表现层负责。双方用明确阶段或状态通信。

## 制作成熟度

| 阶段 | 设计问题 | 典型产物 |
|---|---|---|
| 任务定义 | 为什么做、玩家获得什么体验、设计边界是什么 | 任务简报、体验目标、范围与主要依赖 |
| 流程架构 | 玩家如何推进、任务如何分段、状态如何转换 | 玩家旅程、任务节拍、状态流、一级需求 |
| 实现规格 | 系统如何判断和执行、资源如何配套 | 目标与条件、动作与参数、异常处理、二级需求 |
| 逻辑原型 | 核心流程能否闭合并恢复 | 可走查流程图、关键状态原型、验证记录 |
| 质量验证 | 配置、体验和表现是否达到交付标准 | 配置审查、运行验证、问题修订与验收记录 |

### 内部术语兼容

若项目资料使用“L0”“L0q1”“L0q2”“粗拆”“细拆”或“白盒”等内部叫法，先根据实际产物映射到上述阶段；引用来源时可保留原词，但默认交付使用专业阶段名称。不要仅凭等级编号推断完成度。
