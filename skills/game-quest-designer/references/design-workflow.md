# 任务设计工作流

优先使用项目现有模板。缺少模板时，按交付成熟度选择最小字段，不一次填满所有列。

## 任务定义

从剧本、场景叙事分配和项目画像提炼：

1. 玩家在这段任务中的核心体验、已知信息、动机与预期变化。
2. 任务在主线、区域或角色内容中的作用，以及明确的范围边界。
3. 初步任务结构、主体功能需求、关键演出和主要资源依赖。
4. 系统层与表现层的协作边界、风险和待确认项。

回退结构：基本信息；设计目标；玩家体验；范围与非目标；流程概览；主要系统需求；资源与演出需求；风险和待确认。

## 流程架构

把任务设计到足以评审玩家旅程、节奏、任务边界、状态转换和主要制作依赖的程度，不提前伪造精确参数。

每个任务单元至少说明：稳定 ID、叙事节拍、玩家信息与行为、进入条件、核心目标、反馈、结束状态、前后依赖和一级功能/资源需求。若项目采用 Quest 模型，再补领取/提交模式和可见性。

判断任务边界时，优先看玩家目标、决策上下文或持久状态是否发生有意义变化，而不是按对白段落、地点切换或预计时长机械分段。相邻节拍若目标及失败/恢复语义相同，可保留在同一任务单元中。

## 实现规格

将确认后的流程架构映射为可配置、可开发和可验证的系统语义：

- 目标类型、参数、运算符、值、计数范围和显示文案。
- 启动条件及 `and/or` 关系；开始、成功、失败各阶段动作。
- 可见性、奖励、前置/后置状态及异常恢复。
- 对话、Timeline、NPC、音效、特效、镜头等二级制作需求。

所有类型、枚举和字段须来自真实 schema 或配置库。未知时保留“期望行为 + 待映射字段”，不要生成貌似可用但未经证实的配置。

## 交付检查

- 每个节拍能从剧情流追到玩家行为，再追到系统条件和结果。
- 流程架构不把实现猜测写成确定能力；实现规格不掩盖 schema 缺口。
- 表现动作与任务状态分工清楚，关键状态变化有明确恢复目标。
- 新增需求和复用候选均保留来源 ID。
