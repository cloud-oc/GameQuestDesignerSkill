# 剧本拆解与系统映射

## 从叙事到玩家行动

先识别剧本的因果链、关键事实、角色动机、必须保留的转折及结局。区分作者知道的信息和玩家在此时能知道的信息。不要把每段对白机械转换成一个目标。

拆解成有体验意义的节拍，用稳定 ID 关联三层内容；可以用一张表表达，不必复制三份：

| 关联 ID | 剧情流 | 玩家体验流 | 任务逻辑流 | 系统依据/缺口 |
|---|---|---|---|---|
| 项目已有 ID 或临时 B01 | 谁因何行动，发生何事 | 玩家知道什么、想做什么、实际做什么、得到什么反馈 | 进入条件、有效事件、状态变化、退出条件 | 对应已有能力和来源，或待确认 |

对白、过场、玩家可操作段分别标明。将“角色决定”“时间流逝”等叙事描述转成可观察事件之前，先确认玩家是否参与，以及系统怎样知道它发生了。

## 明确任务逻辑

按本项目表达每个步骤所需的前置条件、目标对象、有效事件、计数范围、完成判定和后续状态。分支写明条件、结果与汇合点；并行目标写明全部满足还是任一满足。没有项目结构时用中立伪逻辑，不编造节点名。

特别检查实际涉及的情况：

- 玩家先拿道具、先杀目标或从非预期入口进入时，是追认、阻止还是提供替代？
- NPC 死亡、失踪、离开加载范围或被其他任务占用时，流程如何继续？
- 演出跳过、交互取消、离开区域和失败重试会留下什么状态？
- 读档、重入和事件重复会否重复计数或发奖？奖励只在何种合法状态变化时发放？
- 关键道具被消耗或交付后，目标判定是否仍然合理？
- 联机项目的任务状态归属、队员差异、同步及掉线恢复；单机项目无需此项。

只检查相关项。系统行为未知时给出设计目标及待验证点，不宣称已有存档、锁定或去重能力。

## 映射与缺口处理

将每个关键行为对应到有依据的项目能力。无法映射时给出：期望体验、缺少的能力、现有能力可实现的替代方案、体验损失、保留原设计所需新增依赖。替代方案也必须有能力依据；如果没有，只能作为候选。

若用户要求配置文件，先核对真实 schema、字段类型、枚举和引用 ID；区分可交付配置、缺字段的草稿和中立伪逻辑。使用项目验证器时记录真实结果，不用 Markdown 逻辑评审代替引擎验证。

最后从开端沿每条主要分支走到合法终态，检查阻塞、无入口、无出口和状态冲突。交付必要的改编说明，再按需提取制作需求。
