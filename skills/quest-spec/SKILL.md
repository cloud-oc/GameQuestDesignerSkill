# 任务实现规格

## 开始之前
先看用户提供的项目资料和模板，只做这次需要的内容。资料不全时，可以先写草案，把假设和待确认的问题说清楚。沿用已有编号，注明关键规则的来源；其他项目的做法只能作为建议。
涉及引擎配置时，以真实格式和项目能力为准。交付时说清检查过什么：文档走查、配置校验和引擎运行是不同的验证，不能互相替代。

## 怎么把设计说清楚
像向一起做任务的策划说明方案：先讲玩家遇到什么、要做什么、会发生什么，再补规则和制作细节。每段围绕一个问题，优先用完整短句；只有需要对照条件或分支时才用表格。
首次出现“节拍”“状态”等术语时，用当前任务解释。例如“询问船工后，玩家得知货物被运往旧仓库”，比“完成信息反馈与状态流转”更清楚。沿用项目已有术语，但不要堆叠抽象名词。
创意草案先让人读懂故事和玩法；交接规格再补编号、条件和字段。把事实、建议与待确认事项分开说明即可，不必给每句话贴标签。

## 规格方法
涉及存档、异步事件、共享对象、联机或旧内容升级时，读取 [运行时行为与开发交接](references/runtime-contracts.md)，明确状态所有权、持久化、副作用与恢复结果。
识别真实 schema、样例、条件/事件库和 ID 规则。资料不足时交付中立状态与行为规格，配置映射保持待确认。
每次状态转换写明：来源状态、条件组合、有效事件、状态变更、动作顺序和后续状态。区分监听一次事件和检查持续满足的状态。
每个目标明确对象范围、计数单位、累计/当前值、起算时间、重置条件、可选性与完成语义。例如“持有三件”与“接取后获得三件”不能混写。
声明奖励领取资格、消耗物品与发奖时机，以及重复事件的预期结果；未确认事务或去重机制时，把它们写成实现要求。
声明式项目将表现调度交给对应表现层，任务层保存可恢复的进度；明确双方通信、持久检查点与恢复责任。
对分支变量说明写入时机与有效期，避免状态互相覆盖。联机项目再补归属、队员差异与离队语义。
## 交付
使用项目模板输出目标表、转换表与异常处理。附字段/枚举/资源 ID 的映射证据及未解决项。
项目没有现成模板而用户需要完整可审阅规格时，按需复制 [实现规格模板](assets/quest-implementation-spec-template.md)。模板表达中立行为语义，不替代真实 schema。
用户要求机器配置时，仅使用已证实字段；运行项目验证器后报告具体输入和结果。不要将逻辑自洽等同于可以导入。
## 验收场景
覆盖本任务相关的提前满足、重复交互、物品先消耗后判定、失败重试、读档/重连和奖励重复请求。记录初始状态、操作、预期状态、预期副作用。
